# iOS 主畫面網頁 App 啟動交接閃白一格：一整天的追查紀錄與結論

> 給之後要做 Launch Screen（啟動畫面）的任何專案看的。先讀第 1 節的結論與第 2 節的教訓，能省下一整天。
> 日期：2026-10-29。裝置：iPhone（iOS 27）。比較對象：NekoServe 網站版（同一支手機）。

## 1. 結論

**症狀**：從主畫面冷啟動網頁 App，iOS 的啟動圖（`apple-touch-startup-image`）換到 WebKit 第一格之間會露出一格白色。只有一格（8 到 16 毫秒），肉眼明顯，螢幕錄影錄不到。深色主題看起來像閃光燈；淺色主題看起來像插圖淡掉又回來。

**原因**：這是 iOS 的行為（WebKit bug 311569，2026 年 4 月開立，仍未修）。iOS 先把啟動圖拿掉、露出視窗的白色底，再把 WebKit 的第一格蓋上去。頁面的任何寫法都壓不掉：樣式表擋不擋繪製、Service Worker 有沒有、manifest 的掛法與欄位、`theme-color`、`color-scheme`、啟動圖的張數與 media 寫法、App 內的停留畫面、玻璃（backdrop-filter）、預先載入、第一格有沒有文字、load 事件早晚、啟動後改不改網址、主機是 Workers 還是 Pages、HTTP 標頭，全部用實機對照過，一個都沒有差別。

**為什麼有些 App 看起來沒有這一格**：白的那一格接在淺色畫面前後時看不見。只要「啟動圖」和「WebKit 第一格」有一邊是淺色，就感覺不到閃；兩邊都是深色時才會看到閃光燈。NekoServe 看起來無縫，是因為它剛裝好時主題預設淺色；把它的主題設成深色就一樣閃。

**決定**（維護者，2026-10-29）：接受這一格，啟動圖與停留畫面照常跟著主題（深色主題用深色啟動圖，淺色用淺色）。理由：淺色配淺色本來就看不到；深色配深色那一格是平台的，Apple 修好 311569 就消失；試過的替代做法「啟動圖與停留畫面一律淺色、深色頁面在淡出時才接上」實機看起來是淺色畫面突然跳成深色，不比原本好，而且啟動圖就不跟主題了。這個替代做法的程式改法留在第 5 節，之後想換再用。

## 2. 最重要的教訓（這一天大部分時間都踩在這些上面）

1. **比較閃不閃，一定要「深色啟動圖加深色第一格」。** 淺色會把那一格藏起來，讓人以為某個改動修好了。本案的深色主題只靠 `data-theme=dark` 套用，而這個屬性是啟動腳本設的；凡是把啟動腳本拿掉或拆掉主題那一段的實驗版本，頁面其實變成淺色，於是「不閃」。二十幾個「不閃」的結果，事後發現沒有一個是深色頁面。檢查方法：加入主畫面前先確認頁面本身是深色的，再看交接。
2. **只有肉眼和 240 格慢動作算數。** 螢幕錄影（60 格、啟動時還會丟格）錄不到單格；iOS Simulator 錄影逐格看完全不重現；桌面瀏覽器的自動化量不到交接。
3. **單次觀察不可信，每個版本至少冷啟動五次算比例。** 同一個版本連續兩次沒閃、換一天五次全閃的事發生過。冷啟動的定義：先從多工列把 App 滑掉再點圖示。
4. **先證明環境無關，再逼近。** 把對照組的 App 整個搬到會閃的網域（HTML、資源、Service Worker、manifest、啟動圖）確認主機與標頭出局，再一次只改一項。這個方法本身是對的，壞在第 1 點：沒有先確認對照組與實驗版的第一格都是深色。
5. **寫下每一輪的變因與結果**，不然到第十輪就會忘了哪些已經排除、哪些實驗其實無效。

## 3. 症狀的觀察紀錄

- 深色：啟動圖（夜空色）之後整張白一格，再接 App 畫面。淺色：中間那一格只有底色沒有插圖，看起來像插圖淡掉再回來。
- 交叉觀察（定案的關鍵）：淺色啟動圖接深色頁面不閃；深色啟動圖接淺色頁面不閃；只有深接深閃。
- 時間點：在「啟動圖換到 WebKit 第一格」的交接，不在 App 自己的淡入前後；App 內做淡入遮不住它。

## 4. 走過的岔路（按時間，每條：假設、怎麼測、結果）

### 4.1 前兩天
- 啟動圖與 App 內停留畫面同一張圖、至少停 1.5 秒：交接時插圖往下跳 25 點，是主畫面 App 的視窗從狀態列底下開始（WebKit bug 301994），首次繪製前量 `screen.height` 減 `innerHeight` 補回去，對齊修好。
- 以為白一格是「樣式表載完前 WebKit 整頁不畫」：入口樣式表改成不擋繪製。第一次繪製從三秒多提早到兩百毫秒內，那一格還在。縮短空白不等於消掉那一格。
- 查到 WebKit bug 311569，一度結案為平台行為。這個判斷是對的，後來被自己推翻又繞回來。

### 4.2 當天的對照實驗（三十幾個版本，用 Workers 版本預覽網址部署，實機加入主畫面）
依序測過：沒有停留畫面、樣式表擋繪製、不註冊 Service Worker、拿掉啟動圖、theme-color 改深色、viewport 拿掉 interactive-widget、第一格放文字或圖片、啟動圖連結 media 改對方寫法、只留深色圖、玻璃改實色、不畫 Tab bar、manifest 加 display_override、純靜態頁（沒有 JS）、對方的 HTML 原封不動搬過來、對方的 HTML 加 React、加它真正的 manifest、加它真正的 Service Worker（資源全鏡像到同網域）、同一個靜態頁放到對方的 Pages 上、body 空的 1 秒後才放內容、最簡單的 Service Worker、把 load 拖後、第一格之後用 replaceState 改網址、對方整個 App 放到我們的根路徑、我們的 App 逐項改成對方的樣子（manifest 掛法與欄位、停留畫面、樣式表、預先載入、Service Worker、啟動圖）、啟動腳本整段或分段拿掉、Tab bar 改絕對定位、內容延 0 到 1000 毫秒出現。
- 看起來「不閃」的：對方的 App（剛裝好是淺色主題）、所有把啟動腳本或它的主題段拿掉的版本（頁面變淺色）。
- 看起來「閃」的：其他全部（頁面是深色）。
- 中途兩個錯誤結論：「玻璃的 backdrop-filter 是原因」（對照組是淺色頁面）、「從子路徑安裝一律會閃」（子路徑的實驗頁都是深色靜態頁，根路徑的「不閃」版都是淺色）。兩個都在五次計數加交叉觀察後推翻。

## 5. 沒有採用但做過的替代做法（啟動圖與停留畫面一律淺色）

```ts
// 停留畫面的 style（內聯在 index.html）：不分主題一律紙色
`html[data-display=app] #ll-launch{...;background:${THEME_COLOR.light};color:${lightText};...}`
// 啟動圖連結：只有淺色一套，media 不帶 prefers-color-scheme
`<link rel="apple-touch-startup-image" media="screen and (device-width: ${w}px) and (-webkit-device-pixel-ratio: ${dpr}) and (orientation: portrait)" href="/splash/apple-splash-light-${w * dpr}x${h * dpr}.png">`
```

實機結果：交接確實看不到白的那一格，但淺色停留畫面淡出成深色頁面（0.25 秒）在深色模式下看起來像淺色畫面閃一下再跳成深色，而且啟動圖不再跟主題，維護者覺得不比原本好，沒有採用。要用的話淡出時間至少要拉到 0.6 秒以上，並接受深色使用者先看到淺色畫面。

## 6. 給新專案的檢查清單（iOS 主畫面網頁 App 的啟動畫面）

1. 白的那一格是 iOS 的，壓不掉；要讓人看不見，啟動圖和第一格至少一邊要是淺色。先決定要不要為它犧牲「啟動圖跟主題」：本案決定不犧牲，接受深色配深色會閃一格。
2. 要有 `<meta name="apple-mobile-web-app-capable" content="yes">`，iOS 才會下載 `apple-touch-startup-image`；只靠 manifest 的 `display: standalone` 不夠。
3. 主畫面 App 的視窗可能從狀態列底下開始、比螢幕矮（WebKit bug 301994）：覆蓋層用百分比版面時，在首次繪製前量 `screen.height` 減 `innerHeight` 補回去。
4. 啟動圖在「加入主畫面」那一刻固定；要測得刪掉重加。
5. 看那一格只能靠肉眼或 240 格慢動作，每版至少五次冷啟動；錄影與 Simulator 都不算數。
6. 做對照實驗前先確認兩邊的第一格都是深色，否則結果全部無效。
7. 和這一格無關但同一天踩到的坑：Workbox 的 precache 逐項下載（292 項從台灣約 60 秒，改並行後 13 秒）；`wrangler dev` 的 ETag 不隨檔案改變，`registration.update()` 永遠拿到 304；跨網域 precache 會因 `cache: reload` 觸發 CORS preflight 而失敗；Cloudflare Workers 的資源上傳 API 一天幾十次後會暫時拒絕，等十分鐘再試；建置外掛用正則改 `<link rel="stylesheet">` 時會誤改啟動腳本裡長得像的字串。

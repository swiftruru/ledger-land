## 1. 開工前的決定（2026-10-23）

## 6. 和計畫不同的地方

1. **核心資料的位置**：科目表、範本、指標、版面放 `packages/core/data/` 適用 MIT（第 1 節），不在 `content/`；`content:check` 的範本來源跟著改。
2. **版面列的 kind 擴充為 15 種**：04 第 11.6 節只示範幾種；實作需要 `inventory_overage`、`noncash_addback`、`retained_earnings`、`group`、`balance_begin`、`balance_end`、`total` 等，每種的必填欄位在 schema 寫死。04 第 11.6 節改為節錄並指向 schema 與資料。
3. **TraceRule 擴充**：04 第 2 節原列六種，實作依版面列的 kind 擴充為 12 種；`TraceAccount` 多 `opening` 欄位；`Statements` 多 `policyId` 與 `source`。
4. **`validateEntry` 回傳 `CoreError[]`**（空陣列表示通過），不再包成 `Result`；`solveScenario` 多 `options.stories`。
5. **情境事件過帳成一步 `scenario`**：計算型題目的 `events` 以一步過帳，而不是每個事件一步；`effects` 的 `text` 只代入名詞佔位符，另有 `unchanged` 方向。
6. **lock 檔新格式多 `removedOptionIds`**：實作 `id.optionReused`（08 第 4.4 節）需要記住被移除的選項 ID。
7. **xlsx 採自製讀取器**，不用 SheetJS：老師的檔案文字全是 inlineStr、公式格沒有快取值，公式只用到 SUM、IFERROR 與四則運算，用 node 內建的 zip 解壓與 XML 解析就夠（14 第 5.3 節已完成）。
8. **攤銷範本沒有前置條件**：`tpl.amortise_org_costs` 若比照折舊範本加「設立費餘額大於 0」的前置條件，會改變 `ifrs@1` 下「本筆無影響」的行為，需要 `Precondition` 支援 `policyWhen`；M1 的 `Precondition` 不支援，所以先不加（第 8 節的 L3）。
9. **04 第 6.4 節範例的 `is_cogs` 公式**實際多一列存貨盤盈（`teacher@1` 下為 0），文件的範例可再補。

## 7. 新發現

1. **平行實作時 schema 與資料分歧**：content-schema 與 core 平行寫出的版面形狀不一致，以核心資料為準改 schema，並加 `schema-conformance.test.ts` 守住。之後凡是兩邊同時改的形狀，先定資料再寫 schema。
2. **Node 的 strip-only 模式不支援 constructor parameter property**：`content:check` 與 `content:lock` 直接以 node 執行 TypeScript，core 原始碼已改寫，規則記在 09。
3. **名詞與科目、版面列的 label、aliases、flags 必須逐欄一致**：目前靠人工與 conformance 測試守住；建議 M2 在 `content:check` 加比對（04 第 4.1 節）。
4. **Lighthouse 名詞頁 LCP 一次超標**：main 的 ci 在執行器波動下量到 2740 ms（門檻 2500 ms），重跑為 2321 ms，程式沒有改動；M0b 第 8 節第 11 點的改善仍有效，但名詞頁離門檻最近，M2 加內容後要再量。
5. **CI 時間與 PR 的瘦身**：M1 之後 main 的 ci 一次跑到 44 分鐘（三個瀏覽器的 E2E 加 5 次 Lighthouse，含執行器排隊），當天 GitHub Actions 的額度用滿，資料同步的 PR 以本機全套驗證（888 個測試、typecheck、lint、content:check、build、update 與 offline 與 shell 的 E2E）為準合併，main 的 ci 之後重跑綠燈。之後 PR 只跑 Chromium 與 3 次 Lighthouse（約 5 分鐘），main 維持完整（約 9 分鐘）。
6. **rebase 合併與疊 PR**：M1 的 PR 以 rebase 合併並刪分支後，疊在它上面的 PR 被自動關閉，改以 cherry-pick 開新 PR 合併，沒有強制推送。之後疊 PR 時，合併底層 PR 前先把上層 PR 的 base 改到 main。
